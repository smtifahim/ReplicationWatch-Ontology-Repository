# CDBO v0.4.1 and CSDO v0.1 build bundle

Two ontologies, both generated by scripts, both draft:
- cdbo-core-v0.4.1.ttl: the ClaimsDB metadata ontology. Since v0.3: Claim_Age_Group; v0.4 adds Morphometry_Method (study), Claim_Sex_Group (claim), Imaging_Modality_Mapped_Curie and Imaging_Modality_Unmappable (study), and sex in the claim-splitting rule. v0.4.1 adds Claim_Laterality_Mapped_Curie and moves measure grounding to PATO.
- csdo-core-v0.1.ttl: the Claim Similarity Dimension Ontology (two classes, Claim Group and Criteria Set; edge properties; the SPARQL queries as annotation properties). It imports CDBO.

The CDBO file is the single source for prompts, JSON schemas, the data dictionary and the Excel workbook. The CSDO file is the single source for the load and portal queries.

## CSDO

    python3 -m venv v04 && v04/bin/pip install pyoxigraph==0.4.11 rdflib     # RDF-star community-group syntax
    cd csdo
    python gen_csdo.py ../cdbo-core-v0.4.1.ttl ../csdo-core-v0.1.ttl            # rebuild the ontology from queries/*.rq
    ../v04/bin/python lint_csdo.py ../csdo-core-v0.1.ttl                      # structure checks and parse every stored query
    cd tests && ../../v04/bin/python run_csdo_flow.py ../../csdo-core-v0.1.ttl         # run the stored queries, compare with an independent implementation
    ../../v04/bin/python demo_contradiction.py ../../csdo-core-v0.1.ttl smaller        # three papers, four claims

- csdo_queries.py reads the queries from the ontology in execution order. The loader runs the two load CONSTRUCT queries after each finished batch (groups first, then edges) and merges each result into the knowledge base. Re-running is safe because group and edge IRIs are deterministic and the merge is a set union.
- Edge properties are RDF-star: the quoted triple is the subject (criteria set, laterality, measure and direction relations, versions used). The reference deployment is Stardog. The queries use standard SPARQL 1.1 plus RDF-star quoted triples, so other graph databases that support RDF-star should need at most dialect changes.
- Tested only in Oxigraph 0.4.11, in memory. Not tested in Stardog, GraphDB or Jena. Check in Stardog: edge.properties enabled when the database is created, the serialized CONSTRUCT output keeps edge properties through the API merge, and an edge and its properties sit in the same named graph.
- Parameters in portal queries are written {{FOCUS}}, {{CRITERIA_SET}} and {{GROUPS}} and are replaced by IRIs.
- If an ontology version change re-grounds terms, rebuild the derived groups and edges (put them in their own named graph so this is a drop and reload).

## Imports

imports/nidm-imaging-slice.ttl is a vendored slice of the NIDM-Experiment ontology (67 terms: acquisition modality, image contrast type, acquisition method, image usage type, data acquisition device) with the original NIDM IRIs. The grounding script maps Imaging_Modality text to these terms and writes the CURIEs to Imaging_Modality_Mapped_Curie. Source: incf-nidash/nidm-specs, nidm/nidm-experiment/terms/nidm-experiment.owl, commit b568043, Apache-2.0. Analysis software is grounded to RRIDs. Morphometry_Method values and strings with no match (for example medial superior frontal gyrus) are held for curators to contribute to NIDM-Terms in InterLex.


imports/pato-imaging-slice.ttl (13 terms: volume, thickness, area, depth, width, length, curvature and their parent qualities, plus bilateral) and imports/bspo-laterality-slice.ttl (left side, right side) are slices of PATO (commit f16927f) and BSPO (commit 21f4b75), both CC BY 3.0, built with tools/extract_obo_slice.py. Grounding is post-processing, like UBERON: the LLM writes the raw text, and the script fills the mapped fields.
- Laterality: Left is BSPO left side, Right is BSPO right side, Bilateral is PATO bilateral (BSPO has no bilateral term; PATO bilateral is a quality term meaning two-sided). Not Specified has no term.
- Measure: the measure text is matched to a PATO quality. A tissue named in the measure is looked up in UBERON and appended, so gray matter volume and white matter volume differ. No match goes to Claim_Measure_Unmappable.
- config/grounding_seed.json holds the seed lookups (editable). python tools/check_grounding_seed.py config/grounding_seed.json imports checks that every CURIE exists in the slices.

## Excel curation workbook

    python build_excel_template.py ../cdbo-core-v0.4.1.ttl ../config/excel_layout.json ../out/cdbo_template.xlsx
    python fill_workbook.py ../cdbo-core-v0.4.1.ttl ../config/excel_layout.json ../out/cdbo_template.xlsx batch.json ../out/batch_01.xlsx
    python read_workbook.py ../cdbo-core-v0.4.1.ttl ../config/excel_layout.json ../out/batch_01.xlsx batch_01.json ../out
    python test_workbook_roundtrip.py ../cdbo-core-v0.4.1.ttl ../config/excel_layout.json ../out

- The layout (tabs, tab order, column order, group colours, widths, banding colour, identity columns) lives in config/excel_layout.json, not in the ontology. Edit that file and rebuild.
- Tabs: Registry_Metadata, Bibliographic_Metadata, SciScore_Metadata, Extraction_Provenance_Metadata (one row per article), Study_Metadata (one row per study), Claim_Record_Metadata (one row per claim), plus README, Lists (dropdown sources) and Data_Dictionary.
- Row 1 is a merged band per property group, row 2 the field keys. Both rows share one light colour per group. The two header rows and the identity columns are frozen. Text wraps by default. Alternate rows are light blue through a conditional-format rule, so sorting does not break it. Definitions are in comments on the field keys.
- Bold keys are filled by the LLM. Italic grey keys are filled by scripts, lookups or SciScore.
- batch.json is a list of {"publication": {...}, "study": {...}, "claims": [...]} records. Each key is routed to its tab by name. Re-running updates rows in place.
- read_workbook.py checks the ontology version stamp, headers, ID uniqueness and links, dropdown values, numbers, JSON cells and empty LLM cells, then validates against the JSON Schemas. Rows are matched by ID, so sorting and filtering are safe.

## What each script checks or produces

- lint_cdbo.py: altLabel present, unique, Capitalized_Snake_Case; label, description, domain and range present; every LLM-extracted field has a prompt whose field equals the altLabel, whose description equals dcterms:description, whose example contains every IAO:0000112 example, and which has a normalization rule; enumerated examples belong to the enumeration; prompt allowed_values equal the datatype; no non-extracted field carries a prompt; the three general prompts exist.
- build_json_schema.py: study.schema.json and claims.schema.json (draft 2020-12). Keys are skos:altLabel. All fields required, no extra keys, enumerations from owl:oneOf as $defs. Only the portable keyword subset is used. Not yet tested against a specific vendor's structured-output validator.
- build_data_dictionary.py: data_dictionary.csv (all columns, UTF-8 with BOM for Excel) and data_dictionary.md (leaf fields).
- assemble_prompt.py: the system prompt and field fragments for one call, read from the ontology. The static prefix is the cacheable part.
- validate_schemas.py: metaschema check, a sample instance built from the ontology examples, and negative tests (extra key, missing key, bad enumeration value, empty claims array accepted).
